Imagine a GPU as a kitchen with 100 chefs (compute units) and a single narrow hallway (memory bus) connecting the pantry (VRAM) to the cooking line. The chefs can chop, mix, and fry very fast, but if the hallway is too narrow, ingredients arrive slowly. The kitchen’s speed is limited by how fast ingredients can move, not by how fast chefs work. That hallway is memory bandwidth: the amount of data that can be moved between graphics memory and the chip each second.

A GPU often needs to read lots of data: textures, vertex positions, colors, depth values. If it can compute a trillion operations per second but can only fetch 500 gigabytes per second of data, many operations wait for data. This is called being memory-bandwidth bound.

Worked example: Suppose a game frame needs to process 10 billion pixels. For each pixel, the GPU must read 4 bytes of color data and 4 bytes of depth data, so 8 bytes per pixel. Total data to read is 10 billion × 8 bytes = 80 billion bytes = 80 GB. If the memory bandwidth is 500 GB/s, just moving that data takes 80 / 500 = 0.16 seconds. That is about 6 frames per second, even if the compute part could finish in 0.01 seconds. The bottleneck is the data movement.

Engineers fix this in several ways. First, they design memory with more channels and faster chips, like making the hallway wider and the pantry workers faster. Second, they compress data so less needs to move. For example, if depth data can be compressed from 4 bytes to 2 bytes, the same frame needs only 40 GB, cutting the time in half. Third, they keep data in fast on-chip caches and reuse it, so the same texture or vertex is not fetched many times.
